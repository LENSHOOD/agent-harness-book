# 第五主案例遴选：证据评审 v1

> 决策日期：2026-08-22。评分用于决定全章级案例，不代表产品综合排名。GitHub 与包下载数据均为时间截面，只是现实影响的代理指标。

## 1. 评审方法

采用访谈中确认的权重：

| 维度 | 权重 | 判断问题 |
|---|---:|---|
| 现实影响 | 25% | 是否形成可观测的用户、开发者或生态影响？ |
| 架构差异 | 25% | 能否补充 Claude Code、Codex、Cursor、DSH 尚未代表的路线？ |
| 一手材料透明度 | 25% | 是否有源码、正式文档、论文或维护者解释可供复核？ |
| 企业可迁移性 | 15% | 设计是否可迁移到多租户、隔离、协议化接入和治理场景？ |
| 社区与学术证据 | 10% | 是否存在独立研究、基准、社区实践与反方材料？ |

评分为 1–5 分。小数不是精密测量，只用于强迫我们显式表达取舍。

## 3. 决策

第五主案例选择 **OpenHands**。

决定性理由不是流行度，而是它补齐了一条其他四个案例没有完整覆盖的架构谱系：

```text
研究型软件工程 Agent
        ↓
事件流式 Agent/Environment 协议
        ↓
Agent 控制面与 Runtime 执行面分离
        ↓
Docker/远程沙箱与可替换执行后端
        ↓
基准、评测与生产 Agent SDK
```

这条谱系尤其适合企业平台架构师理解：为什么“模型循环”与“执行环境”必须是不同的故障域、安全域和扩展域，以及事件溯源、生命周期控制和远程运行时为何会成为生产 Harness 的基础。

## 4. 为什么不是只选现实影响最高的 OpenCode

截至 2026-08-22 的 GitHub API 快照，OpenCode 的 star/fork 指标在四个开源候选中最高；npm 的月下载量也很强。这足以让它进入全书的重要对照样本，但不能自动转化为主案例资格：

1. star、fork、download 不能等价于日活、企业部署或任务成功率；
2. OpenCode 与 Claude Code/Codex 在终端 coding-agent 产品形态上存在较大重叠；
3. OpenHands 的 Agent/Runtime 分离、事件流和评测传统对参考架构贡献更大；
4. 全书仍会在产品横评、provider abstraction、权限模型和生态章节中系统分析 OpenCode。

## 5. 其他候选的保留方式

### Gemini CLI

作为“大厂开源、模型原生、多协议扩展”的对照：重点讨论 MCP、headless、沙箱、subagent 工具隔离和企业管理。

### OpenCode

作为“provider-agnostic 产品平台”的对照：重点讨论多模型归一化、插件生态、权限模式、LSP/工具集成和开放生态带来的兼容性成本。

### Pi

作为全书最重要的反方：它刻意不内置 MCP、subagent、plan mode、permission popup、todo 与 background bash，主张四工具核心加扩展。每当正文提出“平台应该内置某能力”时，都用 Pi 追问：该能力真的属于核心，还是应留给环境、脚本或插件？

### Devin

保留为产品与工作空间体验案例。由于公开架构材料不足，不承担底层机制的关键事实证明。

## 6. 敏感性分析

OpenHands 与 OpenCode 只相差 0.13 分，决策对权重敏感：

- 若把现实影响提升到 40%，OpenCode 会胜出；
- 若把企业迁移性和学术证据合计提升到 35%，OpenHands 优势扩大；
- 若全书改为“终端 coding agent 购买指南”，应改选 OpenCode；
- 本书目标是“企业 Harness 设计与自研参考架构”，因此维持 OpenHands。

## 7. 证据限制

- GitHub 指标容易受曝光、镜像、活动事件和社区文化影响；
- npm/PyPI 下载包含 CI、升级、镜像和重复安装；不同语言生态不可直接横比；
- 厂商自有使用报告存在样本选择和指标口径问题；
- 公开源码代表可观察实现，不必然代表托管产品的完整生产架构；
- 所有产品事实在定稿前都需按版本和日期重新复核。
