# 第一轮研究札记：现代 Harness 与自我进化

> 状态：研究中；时间截面：2026-08-22。本文只记录阶段性判断，最终正文须经过三角验证与引用审计。

## 1. 已确认的核心区分

DeepSeek Harness（DSH）目前最有价值的贡献，是把“智能体运行时本身”显式建模为可组合、可替换、可卸载的插件树，而不是证明了一个已经成熟的自主进化闭环。官方仓库仍标为 developer preview。

Cordis 为此提供两类底层保证：

- 时间可组合性：组件卸载时，其注册、监听器和其他副作用可以沿所有权关系撤销；
- 空间可组合性：组件声明服务依赖，运行时根据上下文变化激活、停用或重组组件。

这使 DSH 成为“可自修改载体”，但可信进化还至少缺少五个外部闭环部件：轨迹与结果采集、失败归因、候选变更生成、独立评估与统计门禁、发布/回滚/审计治理。

## 2. DSH 的架构骨架

官方材料支持如下分解：

1. 运行实例是一棵 Cordis 插件树；模型适配器、工具注册表、会话日志、默认 agent loop 都是插件。
2. 配置由 profile、bundle、用户 patch、home patch 和临时 overlay 分层合成；上层可以替换下层配置行。
3. `dsh-base` 提供模型、工具、持久化、沙箱、审批、设置、凭证与遥测等基础能力。
4. 插件通过共享 Context 获取服务，通过依赖声明决定激活条件，通过 typed event/waterfall 扩展策略，通过 effect 所有权完成结构化卸载。
5. Agent scope 与 host scope 分离，使单会话可以装配不同工具、persona、prompt 与压缩策略，并限制自修改的爆炸半径。

阶段性评价：这是“微内核 + 生命周期所有权 + 分层配置”的运行时，不只是一个新的 coding-agent UI。

## 3. 自我进化的证据链

近期研究逐渐收敛出一种可信流程：

```text
执行轨迹 + 外部结果
       ↓
弱点挖掘 / 失败聚类 / 因果假设
       ↓
生成最小候选变更（prompt、tool、policy、workflow、memory）
       ↓
隔离评估：重复采样 + held-out + 回归集 + 成本/风险指标
       ↓
统计或规则门禁
       ↓
canary 发布 → 监控 → 晋级或回滚
```

几篇互补论文提供了不同层面的支持：

- Self-Harness：弱点挖掘、候选 Harness 修改、回归验证；说明冻结模型时也能获得显著增益。
- Gated Semantic Quality-Diversity：把“提出变更”交给模型，把采样、计量、显著性检验交给确定性代码，直接针对自评噪声与过拟合。
- Living-Harness：把跨任务经验沉淀为情景记忆和修复状态图，说明进化不一定意味着修改可执行核心。
- Hierarchical Self-Improvement：在中等难度环境有大幅提升，但对超出基础模型能力边界的任务无提升；这反驳了“Harness 可以无限补偿模型”的强说法。

## 4. Codex 的代表性设计

Codex 的公开材料呈现出另一条路线：共享核心 Harness，通过 App Server 暴露双向 JSON-RPC 协议，再由 CLI、IDE、桌面和云端接入。

值得进入正文的设计点：

- agent loop 是用户、模型和工具之间的核心控制器；
- 会话中配置变化以追加新消息表达，尽量保持历史前缀和缓存稳定；
- 长会话通过服务端 compaction 形成可继续执行的替代输入；
- 权限不是一个布尔开关，而是 sandbox、approval policy、exec policy、临时扩权和企业托管约束的组合；
- 多 Agent 通过 thread + worktree 隔离，避免共享工作区冲突；
- 企业实践把 UI、日志、指标、浏览器和测试环境变成 Agent 可读、可操作、可验证的环境。

阶段性判断：Codex 最值得借鉴的不是某个工具名，而是“单一 Harness 核心 + 协议化多客户端 + OS 级策略执行 + 环境可验证性”。

## 5. Cursor 的代表性设计

Cursor 的公开研究材料强调 Harness 与模型共同适配，而非假设同一个 prompt/tool schema 对所有模型都最优。其演化路径从大量静态上下文与强 guardrail，转向由模型主动发现的动态上下文。

典型机制包括：

- 将长工具结果外置为文件，让模型按需读取；
- 压缩后仍可追溯历史会话；
- 工具按需发现，避免一次性注入全部 MCP schema；
- 将终端会话同步为文件，统一上下文读取抽象；
- 对不同模型分别调优工具和指令，并通过线上、线下评估持续发现退化；
- 云 Agent 依赖 VM checkpoint/restore/fork、预构建环境与专用 computer-use 子 Agent。

Cursor 自有使用数据还说明：现代 coding agent 的平均工具调用深度、输入上下文占比和自动接纳比例都在快速上升。但这些是厂商内部、排除了 Privacy Mode 用户的观察数据，正文只能作为趋势证据，不能外推为整个行业的无偏统计。

## 6. 第五案例候选的当前比较

| 候选 | 独特教学价值 | 证据透明度 | 与四主案例的互补性 | 当前判断 |
|---|---|---:|---:|---|
| OpenHands | event stream、Agent/Runtime 分离、Docker 执行面、学术基准传统 | 高 | 高 | 暂时领先 |
| Gemini CLI | 大厂开源、MCP、沙箱、subagent、headless | 高 | 中 | 强备选 |
| OpenCode | provider-agnostic、权限与插件生态、终端体验 | 高 | 中 | 强备选 |
| Pi | 极简四工具、刻意不内置 MCP/plan/subagent/permission UI | 高 | 很高 | 适合作为反例或侧栏，也可能入选五案 |
| Devin | 产品代表性强、自治工作空间鲜明 | 较低 | 中 | 公开架构不足 |

最终选择不能只按流行度。建议采用：现实影响 25%、架构差异 25%、一手材料透明度 25%、企业可迁移性 15%、社区与学术证据 10%。按当前证据，OpenHands 领先；Pi 极适合作为“薄 Harness”反方设计贯穿全书。

## 7. 对全书结构的影响

1. “进化”篇必须从可变对象、评价者、门禁与治理四个角度展开，而不是只罗列 reflection/memory 技巧。
2. 参考架构需要同时包含不可变控制平面和可演化数据平面；Agent 不应能直接修改负责给自身打分和授权的根信任。
3. 产品比较应按共同机制比较，而不是按功能清单：循环、上下文、工具接口、执行环境、权限、验证、会话协议、多 Agent、可扩展性、演化接口。
4. 历史篇必须解释从“框架内编排链”到“环境内自主循环”，再到“可观测、可治理、可演化运行时”的范式迁移。

## 8. 下一轮待证实问题

- Cordis 的形式化保证与实际 DSH self-modification 插件之间有哪些未覆盖的安全边界？
- Claude Code、Codex、Cursor 对 stop condition、tool error、compaction loss 和 retry budget 的实现差异是什么？
- OpenHands、Gemini CLI、OpenCode、Pi 的真实采用度，如何用 GitHub、包下载、公开 PR 数据和调查交叉校正？
- Harness 更新的收益如何与模型更新、任务污染、评测方差拆分？
- 企业运行时中哪些状态允许自动进化，哪些必须进入人工或双控制审批？
